# v1.2.0 — compare mode, lanes, the run dashboard, architecture conformance and vendor balancing

Base: core 1.1.1. Discovery mode: `deep` (user). Evidence: an investigator report (GPT-6 Astra
`xhigh`) and a second opinion (Claude Opus) on it; their recommendations are folded in below.

Goal: the orchestrator can (1) have two independent agents produce the same design memo or the
same investigation and see where and why they differ, (2) start every worker the right way —
in-session subagent, headless CLI or a visible herdr pane — by a tested rule, and (3) show the
user a local page with who does what, spend, tripwires and pending gates.

## Design

### Events log

`<run>/events.jsonl`, one JSON object per line: `{"v": 1, "id", "at", "type", …}`. The only
writer is `task_state.py event <task> <type> --data JSON [--id ID]`: it appends under an
exclusive file lock and skips an `id` already present, so a repeated hook delivery is harmless.
Readers skip unreadable lines and count them.

| type | fields |
|---|---|
| `run.start` | `workflow` (dev / discover / investigate), `depth`, `compare` (off / design / investigation), `runtime_mode` |
| `dispatch.start` | `dispatch`, `role`, `runtime`, `model`, `effort`, `launcher` (subagent / headless / pane), `work` (unit or candidate), `report`, `pane` (herdr name or null) |
| `dispatch.end` | `dispatch`, `status` (done / failed / timeout / cancelled), `usage` {`tool_calls`, `input_tokens` (cached input included, so both vendors compare), `output_tokens`, `duration_s`, `cached_input_tokens` when the stream reports it} — each may be null, never guessed |
| `gate.open` / `gate.answer` | `gate`, `card` / `answer`, `source` (the user's words) |
| `compare.start` / `compare.result` | see Compare |

A gate card without a `gate.answer` is pending. `run.md` stays the narrative. Runs without the
log (older runs) render from their existing files, with every missing fact shown as unknown.

Claude Code: the generated hooks write `dispatch.start` on `PreToolUse(Agent)` and on a
background launch, and `dispatch.end` on completion, for dispatches tagged
`[pharos task=… unit=…]`. Codex: the orchestrator calls `task_state.py event`, as it calls
`tripwire.py spend` today; `lanes.py` writes both events for everything it starts.

### Lanes: how a worker is started

`lanes.py decide --role R --runtime claude|codex --orchestrator claude|codex --minutes N
[--needs-user] [--outlives-turn] [--repo PATH]` prints `{"launcher", "reason"}`:

| Launcher | When |
|---|---|
| `pane` (herdr, `HERDR_ENV=1`) | any of: the user will watch or steer (expected > 20 min, a Tier-3 writer, a compare candidate); the agent needs the user's answers or approvals mid-way; the work must outlive the orchestrator's turn; another repository |
| `headless` (`claude -p` / `codex exec`, log file) | another vendor than the orchestrator, short, report-only, no questions; or a `pane` decision without herdr |
| `subagent` | same vendor as the orchestrator, short, report-only, result needed before the next step |

`lanes.py start` launches by the decision and writes the events; `status`, `wait`, `result`,
`cancel` work the same for every launcher; `cancel` ends the lane and never delivers a pending
brief to a pane. Headless runs use `--output-format stream-json`
(Claude) or `--json` (Codex) for liveness and usage, and `--max-budget-usd` where it applies.
Herdr: at most 3 live agents counting ones already running (otherwise queue, or headless for
report-only work); a tab per run once it has two panes; another repository gets its own tab;
panes the run did not create are never closed or reused. Owner amendment (2026-10-10): for a
`blocked` agent, read the actual dialog; answer questions you can decide from the spec and earlier authorizations;
never answer trust/permission reviews; escalate material decisions to the user. Scripts surface
the condition without sending automatic input. A Codex pane carries the guard by `-c
hooks.PreToolUse=…` as headless does; usage from a pane is null.

### Compare

Offered in the start question with the depth mode, default off, recommended with its signal:
design — two or more real architectural options with different consequences; investigation — a
costly decision, conflicting evidence, or low confidence after a deep pass.

Common rules: one frozen input (the written interview record or the investigation brief,
checked for completeness, hashed); fresh contexts that never see each other's work until
sealed; equal capability profiles (a shell, the source, writes only in the candidate's scratch directory) or
the result is labelled `capability-unequal`; a candidate works in a candidate snapshot (an
independent shallow clone of HEAD plus the working changes), never in the source checkout, and
`lanes.py snapshot-cleanup` removes it afterwards; all slots reserved in one locked append before any
launch; candidates write their report as they go; `user_steered` is recorded per candidate (headless: false; pane: unknown, since herdr cannot
attribute input); the user reads the arbiter's or the map's output verbatim, not only the
orchestrator's summary; state resumes from the events log (sealed candidates are reused).

- **Design (`compare.py design`)** — two competitors write a 1–3 page approach memo each
  (design, contracts, failure handling, cost, risks, evidence). An arbiter that wrote neither and is
  not weaker than them compares the memos against the rubric twice, with labels anonymised and the
  order swapped; a flipped verdict is reported as `arbiter unstable`. Default pairs: standard —
  Claude `implementation` vs Codex `implementation`, arbiter Codex `critical-review`; deep — Claude
  `deep-reasoning` vs Codex `deep-reasoning`, arbiter Claude `escalation`. Output:
  `comparison.md` and `judgement.json` (`ranking` or `tie`, failed mandatory requirements grouped
  by requirement row, disagreements (exact duplicates dropped, never merged by similarity), confidence,
  input hash, stable, `none_meets_mandatory` — said first in the summary when every memo fails one). The user picks one or asks for a merge; a merge
  gets one review before it becomes the basis of the spec. One spec is then written as today.
- **Investigation (`compare.py investigation`)** — two independent investigators
  (`deep-reasoning`, one per vendor), then each critiques the other's report (`critical-review`).
  Output: a disagreement map — claims both make, claims in dispute with both sides' evidence,
  and the cheapest observation that would settle each. A dispute on the answer lowers the
  confidence to low until settled.

Rubric (both kinds): requirement coverage, grounding in evidence, alternatives and uncertainty,
feasibility and cost, actionability. A failed mandatory requirement cannot be outweighed.

### Dashboard

`dashboard.py <task> [--out PATH]` writes `<run>/dashboard.html` (default; for a legacy run without a run directory,
`<primary>/.harness/dashboards/<task>.html`), one self-contained
file without external assets or network requests. First screen: running and stale dispatches
(who, model, launcher, pane, since when), pending gates, tripwires, spend per unit in each unit
(tool calls, tokens, duration; unknown stays unknown), compare status. Then history. It reads
the events log and the existing files, calls `tripwire.check` without recording, links reports
by relative path inside the run directory (no embedded report text), escapes everything, and
writes only under `.harness/`. `lanes.py` and the generated hooks regenerate it after each
recorded transition; it can also run on demand.

### Architecture conformance

Added at the user's request during implementation: «проверка соответствия архитектуре проекта.
Чтобы ничего не расползалось и все было на своих местах по классам, директориям» — in v1.2.0,
script + role + placement.

- **`architecture.json` (overlay)** — the project's declared architecture: `layers` [{`name`,
  `paths` (globs), `may_depend_on` [layer names]}]; `imports` [{`files` (glob), `pattern`
  (regex with a `target` group), `resolve` {prefix → checkout path}}] — how to read a file's
  dependencies in its language; `placement` [{`kind`, `files` (glob of what the rule is about),
  `allowed` (globs where such files may live), `claim`}]; `naming` [{`files`, `pattern`,
  `claim`}]; `roots` [globs] — every file under a root must belong to a layer. No file → the
  check is off (exit 0, says so).
- **`arch_check.py [--base REF | --all]`** — checks the changed files (committed, staged,
  unstaged and untracked against REF, like the other checks) or the whole tree: a dependency
  from a layer to one it may not depend on, a file outside every layer under a root, a file of a
  kind outside its allowed places, a name off its pattern. Findings `path:line — claim`; exit 0
  clean, 1 findings, 2 configuration error. A project adds it to `gates.json`, so CI runs it.
- **`architecture-reviewer` (core role, read-only, `critical-review`)** — a panel lens on every
  Tier 2–3 milestone: reads the project's `architecture.md` (overlay; the map in prose) and
  `architecture.json`, the spec's Placement section and the diff, and arbitrates what a script
  cannot: the right module for each new thing, one responsibility per unit (class, module,
  file), names that say what things are, no second implementation of something that exists, no
  layer doing another's job, directory structure a newcomer can follow. Goal-first like the other
  reviewers; it confirms `arch_check.py` ran.
- **Placement section in specs** — `pharos-discover` writes `## Placement`: for each new or
  moved piece, where it goes and why (layer, module, file). The architecture reviewer checks the
  diff against it; a deviation is a finding unless the spec was amended.
- **`design-review`** reads the same map, so the PR-level pass and the milestone lens agree.

### Vendor balancing

Added at the user's request during implementation: when Claude and Codex work together, the
orchestrator picks each worker's vendor dynamically from how fast each one's limits burn, so both
last longer at the same quality — «модели были аналогичны по мощности для конкретных задач»; in
v1.2.0; minimum share 30 %.

- **Usage (`balance.py usage`)** — per vendor and window {used (0–1), window_minutes, resets_at,
  observed_at, source}: Claude from the latest `rate_limit_event` in a stream lanes captured
  (`unifiedWindows.five_hour`, `seven_day`); Codex from the newest session file under
  `~/.codex/sessions/**/*.jsonl` (`rate_limits.primary` / `secondary`); a manual
  `balance.py usage set` overrides; cached machine-wide (`$XDG_STATE_HOME/dev-harness/` or
  `~/.local/state/dev-harness/vendor-usage.json`). No data → unknown, treated as neutral and said.
- **Equal power** — the vendor is chosen inside one profile of the merged `models.json`
  (implementation: Opus medium ↔ Sol high; critical-review: Opus high ↔ Astra medium; routine,
  mechanical, deep-reasoning likewise), never across profiles.
- **Pick (`balance.py pick --task T --profile P --role R [--not-runtime X]`)** →
  {runtime, model, effort, reason, shares, usage}. Runway per window = (1 − used) / (1 − elapsed
  fraction of the window); a vendor's runway is its smallest. Excluded: used ≥ 0.85 in any window;
  both excluded → exit 6 (ask the user). A runway < 1 once a quarter of the window has passed
  (it would run out before reset) is soft: it sends the work to the other vendor, ahead of the
  minimum share, but never causes exit 6 by itself (FM8: early in a window one burst would
  otherwise exclude a vendor). Each vendor keeps ≥ 30 % of the run's dispatches (from the
  events log); otherwise the larger runway wins, switching only when the gap exceeds 0.15
  (hysteresis). `--not-runtime` keeps a review on the other vendor. Overlay
  `project.json → balance` {min_share, stop_at, hysteresis, min_elapsed} may change the
  defaults.
- **Where it is used** — pharos-dev picks every writer and reviewer through `balance.py pick`
  (compare candidates stay one per vendor); each pick is a `balance.pick` event; the dashboard
  shows each vendor's windows, runway and share.

### Skills and docs

`pharos-discover` and `pharos-investigate` add the compare choice to the start question and the
steps above; `pharos-dev` uses `lanes.py decide` for every dispatch and records events; the

the new scripts. Evals: compare is offered only with a signal and respected when declined;
`compare=off` leaves today's deep flow unchanged.

## Decisions

1. One events log instead of a manifest and per-entity schemas (second opinion C1).
2. Design compare at the approach-memo stage, then one spec (C3); investigation compare by
   cross-critique, not a third arbiter (C4).
3. The arbiter is never weaker than the competitors; anonymised labels and an order-swapped second
   pass are mandatory (C5).
4. No money columns: spend is tool calls, tokens and duration, each in its own unit (C6).
5. Architecture conformance joins v1.2.0: a deterministic check plus a reviewer lens plus a Placement section (user).
6. Lanes are decided by a tested rule; herdr panes only where the user watches, answers, the work
   outlives the turn or another repository is involved (user).
7. The cap of critical cross-reviews per run is five, not four; rounds alternate with fix-ups
   without asking until a review passes or the cap is used (user).
